# Connecting Terraform and Ansible: Integration Patterns

<div class="lesson-goal"><strong>By the end of this lesson</strong><p>Build a scoped inventory and retry configuration independently.</p></div>

When combining Terraform and Ansible, how do you dynamically pass the IP addresses, hostnames, and metadata generated by Terraform to Ansible?

Let us analyze the **4 primary integration patterns**.

---

## 1. Pattern 1: Automatic Inventory Generation via Terraform (`local_file`)

Terraform can generate an Ansible `inventory.ini` or `inventory.yaml` file automatically as part of its execution:

```hcl
# main.tf

resource "aws_instance" "web_nodes" {
  count         = 2
  ami           = data.aws_ami.ubuntu.id
  instance_type = "t3.micro"

  tags = {
    Name = "web-server-${count.index + 1}"
    Role = "webserver"
  }
}

# Automatically generate Ansible inventory file
resource "local_file" "ansible_inventory" {
  filename = "${path.module}/ansible/inventory.ini"
  content  = <<-EOT
    [webservers]
    %{ for idx, inst in aws_instance.web_nodes ~}
    ${inst.tags.Name} ansible_host=${inst.public_ip} ansible_user=ubuntu
    %{ endfor ~}
  EOT
}
```

---

## 2. Pattern 2: AWS EC2 Dynamic Inventory Plugin (`amazon.aws.aws_ec2`)

Instead of writing static files, Ansible's official AWS EC2 plugin queries the AWS API dynamically in real time, grouping instances by their Terraform tags:

```yaml
# ansible/aws_ec2.yaml (Ansible Dynamic Inventory Configuration)
---
plugin: amazon.aws.aws_ec2
regions:
  - us-east-1
filters:
  instance-state-name: running
  tag:Environment: dev
  tag:Role: webserver

# Group hosts by tag: Role (e.g. tag:Role=webserver creates group 'role_webserver')
keyed_groups:
  - key: tags.Role
    prefix: role

# Use Public IP address for SSH connection
compose:
  ansible_host: public_ip_address
```

### Running Playbook with Dynamic Inventory:

Install `amazon.aws` and its documented `boto3`/`botocore` dependencies in the Ansible control-node environment. Use credentials scoped to the intended account. Set the playbook target to `hosts: role_webserver`, then inspect `ansible-inventory -i ansible/aws_ec2.yaml --graph` before running. The static-inventory lesson uses `webservers`, which is a different group.

```bash
ansible-playbook -i ansible/aws_ec2.yaml ansible/playbook.yaml
```

## 3. Pattern 3: The `local-exec` Provisioner (Coupled)

Terraform can invoke Ansible immediately after an EC2 instance finishes provisioning:

```hcl
resource "aws_instance" "web" {
  ami           = data.aws_ami.ubuntu.id
  instance_type = "t3.micro"

  # Provisioner runs locally on the machine executing terraform apply
  provisioner "local-exec" {
    command = "ansible-playbook -u ubuntu -i '${self.public_ip},' playbook.yaml # This play must target hosts: all"
  }
}
```
> [!WARNING]
> **Limitations of `local-exec`**:
> - Tight coupling: If Ansible fails due to temporary SSH unreachable, Terraform marks the entire resource as `tainted` / broken.
> - Difficult to re-run configuration management independently of infrastructure apply.

---

## 4. Pattern 4: Decoupled CI/CD Orchestration (Enterprise Gold Standard)

In enterprise CI/CD workflows, Terraform and Ansible are executed as independent, sequential pipeline stages:


| Stage | Success evidence |
| :--- | :--- |
| Provision | Terraform resources and required outputs exist. |
| Wait | Verified SSH and completed cloud-init. |
| Configure | Playbook completes; HTTP and repeat-run checks pass. |


---


## Apply the idea: inspect the handoff

After apply, select only the required non-secret outputs or query instances with environment and role filters. Inspect the inventory graph and host count before running the playbook. Keep private keys outside Terraform outputs and verify that the runner has a network path to the selected addresses.

<details class="knowledge-check">
<summary>Check your understanding: Ansible failed after Terraform succeeded. Should you destroy the VM?</summary>
<p>Usually no. Diagnose reachability, identity, host keys, cloud-init, and the failed task, then rerun configuration. The decoupled stages exist so a transient configuration failure need not replace healthy infrastructure.</p>
</details>
